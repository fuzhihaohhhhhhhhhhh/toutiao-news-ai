## 三、发现并修复的问题

### 3.1 三个真实的代码 bug

#### Bug A：错误处理写对了，但拿错了「工具」

**现象**：访问一条不存在的新闻，本该提示「新闻不存在」（404），实际却报「服务器内部错误」（500）。

**出错代码**：`routers/news.py` 第 1 行

```python
from http.client import HTTPException     # ← 这是标准库里的那个，不是 FastAPI 的
```

**大白话解释**：Python 生态里有好几个同名的错误类，名字一模一样但用法不同。网站框架 FastAPI 的那个可以写「状态码 404、提示信息 xxx」，而标准库那个**不接受这种写法**，一写就直接报错。

就像你要拿工具箱里的锤子，结果拿了隔壁房间一把长得一模一样的钳子——**名字是对的，东西是错的**。

实测报错信息：

```
TypeError: HTTPException() takes no keyword arguments
（意思是：这个错误类不接受带名字的参数）
```

**影响**：所有「查不到新闻」的分支都变成 500。用户看到「服务器出错」而不是「这条新闻不存在」，运维也没法从日志判断到底是代码挂了还是数据没有。

**顺带发现的一件更值钱的事**：把五个路由文件挨个看了一遍，发现**同一个功能有四种写法，其中一种彻底写错了**：

| 文件 | 写法 | 对不对 |
| --- | --- | --- |
| `routers/news.py` | 从标准库导入 | ❌ 用不了 |
| `routers/favorite.py` | 在函数内部从 FastAPI 导入 | ⚠️ 能用，但写法不规范 |
| `routers/history.py` | 在函数内部从 Starlette 导入 | ⚠️ 能用，但来源又不一样 |
| `routers/chat.py` / `routers/users.py` | 文件顶部从 FastAPI 导入 | ✅ 规范 |

**五个文件、四种写法、一种错的**——这是「逐文件用 AI 生成、缺少全局一致性检查」留下的典型痕迹。这个发现比 bug 本身更有说服力，因为它说明问题是**系统性的**，不是一次手误。

**修复**：改成从 FastAPI 导入，同时删掉一个没用到的导入。

**验证**：测试用例 `test_05_不存在的新闻应返回404` 从红变绿。

#### Bug B：改了草稿，但没点「保存」

**现象**：**每次重新登录，拿到的登录凭证都是无效的。** 用这个凭证请求任何需要登录的接口，都返回「凭证无效或已过期」。

而且这个 bug **只在特定时序下暴露**，手动点浏览器是发现不了的——这正是它危险的地方。

**出错代码**：`crud/users.py` 的 `create_token` 函数

```python
if 已经有凭证记录:
    user_token.token = 新凭证          # ← 只在内存里改了
    user_token.expires_at = 新过期时间
else:
    db.add(新记录)
    await db.commit()                 # ← 保存只写在 else 分支里！
return 新凭证
```

**大白话解释**：这个函数干两件事——要么**新建**一条登录凭证记录，要么**更新**已有的那条。

但「保存」这一步只写在了「新建」的分支里。走「更新」这条路时，程序只在内存里把值改了，**没有真正写进数据库**，然后就把这个新凭证返回给用户了。

就像你改完一份文档没点保存——**唯一救你的是办公软件有个自动保存**。这里确实也有一个「自动保存」：项目的数据库连接在请求结束后会自动保存一次。

**问题就出在时机上**：这个自动保存是在**响应已经发给用户之后**才执行的。所以出现了一个时间差：

```
用户拿到新凭证 → 立刻用它发下一个请求 → 此时自动保存还没执行完
                                      → 数据库里查不到这个凭证 → 401 无效
```

**为什么手动点浏览器发现不了**：正常登录后会有页面跳转、加载，中间隔了几百毫秒，自动保存早完成了。**只有「拿到凭证立刻用」才会撞上——也就是只有自动化测试才能挖出来。**

**三个后果，一层比一层重**：

1. 每次重新登录，凭证有一小段时间是无效的（间歇性 401，线上最难排查的那类问题）
2. **过期时间的续期也一直没生效**。凭证有效期是 7 天，用户在有效期内重新登录本该把期限往后延，但因为没保存，7 天一到凭证全失效，而此时「重新登录」也续不上——**用户会被永久锁在门外**
3. 任何不走这个数据库连接方式的场景（比如后台脚本、定时任务），**完全不保存**，功能直接不工作

**修复**：把「保存」从 `else` 分支里移出来，放到 `if/else` 之后，两个分支都走。

**验证**：`test_09`、`test_10`、`test_13` 三条从红变绿。而且测试账号此时已经存在，走的正是「重新登录」这条路径——精准命中了 bug 的触发条件。

#### Bug C：东西被清掉了，门卫才拦住人

**现象**：**任何人都能删掉别人的聊天记录。**

**出错代码**：`crud/chat.py` 的 `delete_session` 函数

```python
# 先删这个会话的所有消息 —— 但只按「会话编号」删，没检查这会话是谁的
await db.execute(delete(ChatMessage).where(ChatMessage.session_id == 会话编号))

# 再删会话本身 —— 这一步有检查
result = await db.execute(delete(ChatSession).where(会话编号 == ?, 用户 == 我))
```

**大白话解释**：这个「删除对话」的功能分两步——先清空对话里的消息，再删掉对话本身。

第二步有权限检查（不是我的对话就删不了），第一步**没有**。而且两步是在**同一个事务里一起提交**的。

结果就是：别人拿着我的对话编号来调这个接口 → **我的消息被清空了** → 然后删对话那步因为权限不符而失败，接口返回「对话不存在或不属于当前用户」（404，看起来像是没删成）→ **但我的消息已经没了**。

就像**门卫确实检查了「你是不是这间房的主人」，但保洁员在门卫检查之前就进去把东西清空了**——门卫事后拦住了你，东西却找不回来了。

实测证据（直接查数据库，不经任何接口）：

```
A 在会话 14 发了一条消息，HTTP 200
越权删除前，PG 里该会话的消息数 = 2
B 删除 A 的会话 → HTTP 404  {"code":404,"message":"会话不存在或不属于当前用户"}
越权删除后，PG 里该会话的消息数 = 0        ← 消息被删了
```

**修复**：删消息之前先确认「这个会话确实属于当前用户」，不属于就直接返回失败。

**验证**：这条 bug 的检测用例是 `test_20`，它从红变绿。

**这里还有个值得单独说的插曲**：这个用例**第一版是「假通过」的**。

因为它一开始是走网站接口去读消息来判断的，而那个「读消息」接口是**先读 Redis 缓存**的——越权删除失败时（返回 404），清理缓存那一步不会执行，接口就从缓存里把旧消息原样返回，看起来「消息还在」。

**缓存掩盖了数据层的真相。** 一个会假通过的测试比没有测试更危险，因为它给你虚假的信心。后来改成**直接查数据库**才真正把这个 bug 抓出来。

### 3.2 一个性能问题：接口首字延迟 33 秒

这是本次最大的一块，解决过程也最能说明「不要猜，要测」。

#### 现象

跑评测时发现：用户发出问题后，要等 **32.9 秒**才看到第一个字。而项目注释里写的是「首字延迟从 3 秒降到几百毫秒」——**实测差了 2 个数量级**。

#### 排查过程：一路做排除法

| 嫌疑对象 | 实测结果 | 结论 |
| --- | --- | --- |
| 本机代理软件（`HTTP_PROXY`） | 走代理 1454ms，不走代理 952ms | ❌ 只差百毫秒级，不是元凶 |
| Redis 缓存 | ping 8ms，计数 0ms | ❌ |
| 文字转向量（嵌入模型） | 469 ~ 1249ms | ❌ |
| 向量检索 | 3 ~ 563ms | ❌ |
| 模型本身（问它一句「说一个字」） | 首字 1.4 秒 | ❌ |

**全都被排除了。** 而且注意最后一条：**同样的模型，简单的提示词只要 1.4 秒**。这说明问题跟网络完全无关，是模型在处理**我们这个具体提示词**时的行为。

#### 找到根因：模型在「思考」，而你看不见

关键突破来自一个不起眼的统计：**数一数流式响应里「内容是空的」的数据块有多少个。**

| 场景 | 用户实际感受到的首字延迟 | **空内容的数据块数** |
| --- | --- | --- |
| 短提示词 | 4462 ms | **27 个** |
| 真实长度的提示词 | 5026 ms | **44 个** |
| 关掉思考模式 | **2641 ms** | **4 个** |
| 换 `qwen-plus` | **717 ms** | 3 个 |

**这 27~44 个「空块」就是模型的思考过程。** 它先在心里想很久，思考的内容也会一个字一个字吐出来，但走的是另一个字段，用户看到的正文部分是空的。

**所以用户感受到的首字延迟 ≈ 模型的思考时间**，跟网络快慢一点关系都没有。

就像你去餐厅点菜，**厨师先在心里盘算了十分钟才开口回应你**——你在外面干等，以为是厨房太远，其实是他在想。

**这个设计在真实提示词下更严重**：项目的提示词里有 8 条严格的答题约束、3 条检索到的新闻、当天日期，一共 1400 多字。用真实提示词测：

```
真实提示词直接调模型           首字 12286 ms
完整流程：
  分类节点    首事件 @  3406 ms
  问答节点    首事件 @  7552 ms
  >>> 用户能看到的首字 @ 17907 ms
  >>> 全流程结束     @ 20848 ms
```

**还发现一个纯浪费的环节**：流程里第一个节点是「判断用户想干什么」（闲聊 / 问新闻 / 要报告），只需要输出一个词。但它用的也是同一个大模型，**也在思考——为了吐一个词花了 3.2~4.9 秒。**

#### 修复：两处改动

| 改动 | 做法 | 为什么 |
| --- | --- | --- |
| 关掉思考模式 | 给模型加参数 `enable_thinking=False` | 保留大模型档次的生成质量，只是不让它先想半天 |
| 分类用快模型 | 把「判断意图」这一步换成 `qwen-turbo` 档 | 只需要输出一个词，用最强的模型纯浪费 |

改动的文件：`config/rag.yml`（新增两个配置项）、`models/factory.py`（拆出「生成模型」和「快模型」两个工厂函数）、`ai_agent/graph.py`（分类节点改用快模型）。

#### 效果（同样 3 道题，前后对比）

| 指标 | 改进前 | 改进后 | 提升 |
| --- | --- | --- | --- |
| 首字延迟 P50 | 32891 ms | **1297 ms** | **25 倍** |
| 首字延迟 P95 | 45503 ms | **2477 ms** | **18 倍** |
| 平均回答耗时 | 32443 ms | **4630 ms** | **7 倍** |
| 全量测试耗时 | 42.5 秒 | **16.4 秒** | — |

**回归测试 20 条全绿**，没有改坏任何东西。

### 3.3 四个工程性问题

| # | 问题 | 大白话解释 | 修复 |
| --- | --- | --- | --- |
| 1 | 数据库日志刷屏 | 配置里开了「打印每条 SQL」，意味着**每一个网页请求都会把完整 SQL 连同参数打到控制台**——参数里带着手机号、密码这类信息。另一个数据库的配置早就关掉了，两个文件不一致 | 改成关闭（调试时可临时打开） |
| 2 | 脚本退出时报 `Event loop is closed` | 数据库连接在「程序已经关机」之后才被回收，回收时去操作一个已经不存在的连接池。结果没错，但日志里一片红 | 退出前显式关闭连接池 |
| 3 | 评测脚本遇到异常整个崩掉 | 服务在跑评测途中重启，脚本抛异常直接退出，**后面的题一条没跑** | 单条失败只记这一条、继续下一条；连续 3 条都是异常就自动中止，并提示「服务可能挂了」 |
| 4 | 拒答判断词表漏词 | 模型回答「这个我**帮不上**忙」是**正确拒答**，但脚本的词表里只有「帮不了」，判成了「该拒答却没拒答」 | 补齐词表 |

**第 1 条还带出一个有意思的技术发现**，值得单独记一笔：

「关掉 SQL 日志」按常规写法是设置日志级别（`setLevel(WARNING)`）——**但这个写法完全无效，日志照样刷屏。**

去读了 SQLAlchemy 的源码才搞明白：当开启「打印 SQL」时，它用的**不是普通的日志对象，而是一个特殊包装类**。这个包装类在输出时**直接跳过了日志对象的级别检查**，自己决定要不要打印。所以设置级别根本没机会生效。

**正确做法是把引擎自己的开关置回关闭状态**（`engine.echo = False`），它会重新生成一个普通日志对象，级别检查才恢复。

我一开始也判断错了（以为是设置顺序的问题），是实测发现不生效、再去看源码才找对方向的。

## 六、过程中纠正的两个错误判断

排查过程中我下过两个错误结论，都靠实测推翻了，一并记下来：

### 错误判断 1：「本机代理是延迟元凶」

一开始看到延迟 33 秒，第一反应是代理问题——因为本机确实开着代理，而且之前踩过代理把「连接被拒绝」伪装成「502 响应」的坑。

**实测推翻**：走代理 1454ms，不走代理 952ms，**只差几百毫秒**，不可能是 33 秒的原因。

### 错误判断 2：「向量库陈旧、和数据库不同步」

评测里模型的回答提到「资料中最近新闻的发布时间是 **2023-08-31**」，但数据库里最新新闻是 2025 年。我据此判断「向量库是旧的，需要重建」。

**实测推翻**：

```
Chroma 向量库：403 条不同新闻 / 419 个片段
最早 2023-08-01、最新 2025-09-22 10:30   ← 和数据库完全一致
```

**向量库是完全同步的，不需要重建。**

真正的原因是**测试数据本身的时间分布极不均匀**：

| 分类 | 条数 | 最新发布时间 |
| --- | --- | --- |
| 国际 | 57 | 2023-10-05 |
| 财经 | 54 | 2023-08-31 |
| 社会 | 51 | **2025-09-22** |
| 国内 | 51 | **2025-09-20** |
| 头条 | 50 | 2024-03-30 |
| **科技** | **50** | **2023-08-31** |
| 娱乐 | 46 | 2023-08-31 |
| 体育 | 44 | 2023-08-31 |

**只有「社会」和「国内」两类有 2025 年的新闻，其余六类全停在 2023 年。**

所以问「今天有什么科技新闻」返回 2023 年的旧闻，是**数据分布决定的正确行为**，不是检索的 bug。

这两个教训指向同一件事：**性能和数据问题不要靠猜，要设计能直接证伪的实测**。

## 九、这些改进怎么讲

如果要在面试或简历里说这些内容，建议按 **「发现问题 → 定位 → 修复 → 用数据验证」** 的结构，而不是罗列技术名词。

**推荐的说法（每条都有数字）：**

> - 独立设计并落地了一套测试与评测工具链（20 条自动化用例 + 压测 + 评测集打分 + 延迟诊断），上线后挖出 3 个真实缺陷：一处异常类型导入错误导致 404 变成 500、一处漏提交导致重新登录的凭证无效、一处越权删除能删掉他人聊天记录
> - 定位到接口首字延迟 33 秒的根因是模型的「思考模式」而非网络问题——通过统计流式响应中空内容块的数量（26~44 个）确认模型在思考，用 `enable_thinking=False` 加意图分类下沉到小模型两项优化，把首字延迟从 32.9 秒降至 1.3 秒（P95 从 45.5 秒降至 2.5 秒）

**两个可以主动说的细节（都体现判断力）：**

1. **「我的越权删除检测用例第一版是假通过的」** —— 因为它走接口判断，而接口先读缓存，缓存掩盖了数据层的真相。改成直接查库后才真正抓到。这个故事说明你理解「测试本身也可能骗人」。
2. **「我两次判断错了又自己推翻了」** —— 一次以为是代理问题、一次以为向量库不同步，都靠实测证伪。这说明你不会停在「我觉得是」，会设计实验验证。

**避免的说法：**

> ❌ 用了 FastAPI、LangGraph、RAG、Chroma、Redis、PostgreSQL 实现了智能问答系统，支持多轮对话。

——堆名词、没数字、没取舍，任何人都能这么写。
